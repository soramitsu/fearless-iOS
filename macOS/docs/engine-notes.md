# macOS wallet engine

The app composes eight WalletCore services through WalletEngineFactory. Construction creates service objects and defers disk reads, the KDF, keychain queries and network requests until a service call. EngineStore serializes wallet and vault mutations. NetworkServices owns node preferences, runtime registries and the RPC connection pool. Balances and fiat prices have independent entry points.

## Storage and recovery

The password-derived scrypt key wraps a random 256-bit data key. IrohaCrypto calls the repository’s scrypt target. The vault stores the salt and cost parameters. Authenticated decryption by CryptoKit verifies the password and the data. The two AES-GCM envelopes have separate domain tags and fresh nonces. The only long-lived unlocked key is a SymmetricKey on EngineStore. Account secrets are decrypted for individual operations. Lock releases the key. Swift, Foundation and the OS control the lifetime of transient string and data copies.

New password wraps use scrypt N=131072, r=8, p=1 (about 128 MiB) with a fresh 32-byte salt and the NFC spelling of the app password. A password unlock accepts the original raw bytes of a legacy N=32768 or N=65536 wrap and upgrades it to the current cost and NFC. A biometric unlock can migrate the metadata format. Updating the password wrap needs a subsequent password unlock. Password recovery works independently of the keychain, so the KDF uses no device secret. Failed attempts start a one-second delay after the fifth failure and double it up to 4096 seconds. A persisted deadline farther than 4096 seconds ahead is clamped and saved.

A password change rotates the 256-bit data key, reseals the encrypted wallet entries and authenticates the public wallet list under the new key. The private journal records the new password wrap, sealed secrets, wallet metadata and any outstanding Touch ID replacement. If the protected item cannot be updated, the new password unlocks the wallet and retries enrollment. Touch ID uses the data-protection keychain, a device-only item, biometryCurrentSet, and an authentication context invalidated on lock. Erasure deletes the journal, files and interrupted writes first, then reports any protected-item removal failure separately.

Vault format 2 authenticates the exact bytes of wallets.json and biometric enrollment state with CryptoKit HMAC-SHA256. The journal retains those bytes for replay. Unlock verifies the MAC before decoding and caches the public records used for address lookup. Signing and backup still require fresh approval and access to the encrypted account. Migrating a legacy vault checks the signing accounts against their encrypted keys and restores their public paths. Legacy names and watch-only addresses acquire their first MAC on migration. Pre-password watch-only wallets acquire their MAC on initialization. An initialized vault requires an unlock to change its metadata. Mnemonic backup returns the words and complete derivation options after approval. Public metadata retains only the path preceding any triple-slash password. JSON export applies WalletCore PasswordPolicy to the export password.

Each replacement writes a 0600 temporary file, calls Darwin F_FULLFSYNC, renames the file, then fsyncs the containing directory. Opening an existing storage directory under the process lease restores its permissions to 0700. Service instances in the same process share one vault actor per storage directory.

## Recovery parity

The reference is fearless/Common/Operation/MetaAccountOperationFactory.swift. Substrate mnemonic imports use SeedFactory, its mini-seed, SubstrateJunctionFactory and the Native sr25519, ed25519 or ECDSA keypair factory. EVM mnemonic imports use BIP32SeedFactory and BIP32KeypairFactory. The displayed BIP-44 path is converted into the Native junction representation. Raw EVM imports use the existing secp256k1 private key directly. SS58 checksum and EIP-55 formatting use IrohaCrypto and the iOS Web3 dependency. Substrate ECDSA follows the iOS Blake2b prehash. Ethereum uses the existing Keccak signer.

Offline test inputs include the shared 12- and 24-word universal wallet vectors, the iOS Unicode Substrate password fixtures and all four existing Polkadot.js keystore fixtures. The fixture has SHA-256 3b6ea60c00eae541c6dc05617b295acf8fc3ad1e097274a6c0dad5c15fbfdbc6 on macOS, iOS, Android and web. The 2,048-word resource is copied from IrohaCrypto’s English vocabulary. WalletCore distinguishes newly created phrases from imported phrases. The current import contract carries a single derived address per ecosystem and has no selected legacy password rule. The L8 contract request in the review-fix evidence describes the options needed to preview NFC and as-typed Substrate salts and restore the selected account from a backup. The current Substrate mnemonic default remains NFKD.

## Networks, units and fees

The bundled catalog contains nine networks and thirteen assets. Network identifiers preserve the remote config genesis hashes and use eip155 decimal identifiers on EVM. Polkadot and Kusama moved balances to their respective Asset Hubs. The engine queries the relay and Asset Hub separately so the UI can show holdings at both locations. Twenty-eight of 38 candidate endpoints matched the expected genesis hash or EVM chain ID. The catalog includes only those 28. The timestamped node-probe-final.json includes each candidate and failure. Substrate uses multiplexed reads with a 45-second idle timeout. Each submit-and-watch subscription has its own WebSocket. Automatic selection can fail over among verified endpoints. An explicit selection confines traffic to that endpoint. Substrate submission requires a secure WebSocket endpoint. Each balance has a 15-second deadline independent of other callers waiting for a shared metadata load. Recheck the catalog with Node 22 or later using `node scripts/probe-nodes.mjs` from the package.

The engine bundles 695,989 compressed bytes of V14 metadata from five finalized runtimes. A matching genesis, spec version and transaction version requires the live Wasm `:code` hash at the requested block to match the snapshot, including on a registry cache hit. The engine verifies the snapshot’s decompressed SHA-256. For uncaptured versions it reads node metadata and applies the same signing checks. A future runtime that changes the pinned transfer encoding or extension order needs a catalog review.

Before signing, the engine compares the complete dynamically encoded call against the pinned pallet and variant bytes, compact asset ID for Assets calls, a zero-byte MultiAddress::Id discriminator, the 32-byte destination and compact amount. Version-4 extrinsics require CheckSpecVersion, CheckTxVersion, CheckGenesis, CheckMortality, CheckNonce, the catalog’s payment extension and CheckMetadataHash in that order. The hubs use ChargeAssetTxPayment. The other three use ChargeTransactionPayment. Additional extensions must have zero-width explicit and implicit types. The signature uses the 64-block mortal era, zero tip and disabled metadata-hash mode.

All Substrate reads for an individual balance reference the same finalized block. Native total is free + reserved. Under Polite/Expendable rules the floor is max(frozen − reserved, 0). When consumers exist and at most one provider remains, the floor also covers the existential deposit. Transferable is max(free − floor, 0). Keep-alive caps this amount at max(free − ED, 0). A recipient’s free balance after a nonzero deposit must reach the runtime ED. [Polkadot SDK native balances](https://github.com/paritytech/polkadot-sdk/blob/master/substrate/frame/balances/src/impl_fungible.rs)

Asset Hub reads Assets.Account and Assets.Asset together with AssetsHolder.BalancesOnHold and AssetsFreezer.FrozenBalances. Total is the account balance plus the held amount. When either a hold or freeze entry exists, the floor is max(asset minimum, frozen − held). Otherwise it is zero. Transferable is the lesser of supply and the account balance above that floor. It is zero when the asset or account status prevents a withdrawal. Keep-alive additionally preserves the asset minimum. The fixture includes both absent entries for USDC and a real account with a simultaneous hold and freeze. [Polkadot SDK asset balances](https://github.com/paritytech/polkadot-sdk/blob/master/substrate/frame/assets/src/functions.rs)

Native fee withdrawal must preserve the sender’s deposit before the call executes, including allow-death and asset-pallet transfers. A sender unable to pay that fee has a maximum sendable amount of zero. [Polkadot SDK transaction payment](https://github.com/paritytech/polkadot-sdk/blob/master/substrate/frame/transaction-payment/src/payment.rs)

### Fee review and maximum

A successful preparation records the exact TransferRequest and quote for 180 seconds. Submission requires that entry to remain current through approval. Substrate refreshes the nonce, mortal block and signed-size partial fee using payment_queryInfo or the transaction-payment runtime API. A fee above the reviewed amount requires a fresh review. EIP-1559 preparation uses `cap = 2 × base fee + priority fee`. Submission signs the reviewed gas limit, cap and priority fee with a fresh pending nonce, provided the latest base fee plus the reviewed tip fits the cap. Legacy BNB Smart Chain signs its reviewed gas price. All values are integers.

ERC-20 calls use `ceil(estimated gas × 1.25)`. A simple native transfer uses the estimate directly. The catalog transfer policy accepts estimates of 21,000 through 2,000,000 gas, with a final gas limit of at most 2,000,000. The maximum per-gas price is positive and at most 10,000 gwei. These are wallet bounds for the supported transfer calls.

Preparation computes a candidate maximum after fees and any required deposit, then quotes that candidate. For the displayed maximum, the native fee reserve is the candidate fee plus 5%, rounded up to a whole base unit. A native transfer subtracts that reserve from the available amount. A token transfer checks the reserve against the native fee balance and preserves the token minimum where required. The displayed maximum cannot exceed the original candidate. If the node can quote the requested transfer but cannot quote the maximum, the maximum is unavailable and the requested transfer can still be reviewed. The submitted fee uses the reviewed quote.

### Tracking and reconciliation

The engine saves the signed transaction hash and pending activity before submission. The per-wallet, per-chain slot is released when the node acknowledges the transaction. Finality tracking continues independently. A definitive submission rejection, finalized ExtrinsicFailed or canonical finalized EVM receipt status 0 marks failure. A send response containing the same EVM hash or an already-known acknowledgment continues tracking. An ambiguous send reply or unconfirmed dispatch emits outcomeUnknown and leaves a pending record. Receipt and finalized dispatch reads retry with exponential back-off from one second up to 15 seconds. EVM tracking has a 30-minute deadline and Substrate tracking has a 15-minute deadline. A local write error after confirmed success preserves the finalized stream result.

Opening Activity and unlocking a locked vault recheck pending records. EVM reconciliation verifies receipt hash, finalized height, canonical block hash and receipt status, and uses gas used × effective gas price when available. New Substrate records persist the signed nonce and era birth. Once the finalized account nonce advances or the era expires, the engine searches the finalized blocks in that 64-block window by extrinsic hash. It checkpoints completed batches and decodes System.Events using the parent block’s runtime. Missing data remains retryable. An exhausted window without a match is displayed as an unknown outcome. Legacy Substrate records lack the nonce and era. A working indexer can resolve them by hash. Relay history reads the indexer’s success flag for both incoming and outgoing transfers and preserves definitive local failures.

The configured relay history indexers serve transfer records with integer Unix timestamps in seconds. Both Asset Hub indexers failed probing. OKLink’s three EVM feeds returned HTTP 401 without an API key. Westend and Sepolia have no configured indexer. The activity service reports the reason for each unavailable chain and still returns local transfers. Node diagnostics and relay history samples are in the evidence directory.

CoinGecko supplies fiat quotes with a 60-second cache. Missing USD prices fall back to four Chainlink feeds configured for iOS, queried over a chain-ID-checked Arbitrum RPC. The engine checks signed price, round completion and age. Failed oracle requests leave other available prices usable.

The engine uses the repository’s Native products and the same two MIT-licensed libraries already used by iOS. Package.resolved records their commits and transitive versions. [BigInt 5.3.0](https://github.com/attaswift/BigInt/tree/v5.3.0) and [Web3 7.7.7](https://github.com/soramitsu/web3-swift/tree/7.7.7).

Public test vectors and the live Asset Hub recording under Tests are offline resources. storage.json names the finalized block, node and runtime version. The deflated SCALE metadata belongs to that same block. A second recording contains the original System.Events bytes from finalized Polkadot Asset Hub block 23,482,738. It includes two successful extrinsics and a Token.Frozen dispatch error. The signed extrinsic fixture was generated independently with @polkadot/types 16.5.6. EVM fixtures use the published EIP-155 and Web3 typed transaction inputs, independently serialized with ethers 6.17.0. Neither JavaScript package is an engine dependency.
