# Import persistence ownership

Generic mnemonic, raw-seed and JSON imports now return an operation that owns
its provisional Keychain writes. Native TON and universal-root recovery use the
same persistence acknowledgement boundary. Derivation recipes and stored tag
formats are unchanged.

The caller must keep the operation through the wallet-store result and commit
only after that result succeeds. A failed write, cancelled/unowned operation,
or failed wallet save rolls back its owned revisions. Acknowledged wallet keys
remain committed even if later cloud upload fails or the initiating controller
has gone away.

The production caller inventory is:

| Caller | Acknowledgement |
| --- | --- |
| AccountImportInteractor | Selected wallet save |
| AddAccountImportInteractor | Existing wallet update |
| AccountConfirmInteractor | Selected wallet save |
| AddAccountConfirmInteractor | Existing wallet update |
| BackupPasswordInteractor | Restored wallet save |
| GetPreinstalledWalletInteractor | Imported wallet save |
| BackupCreatePasswordInteractor | Local wallet save, before cloud upload |

A process-local ordered revision ledger prevents an older failed import from
removing a newer committed import, including identical-byte writes. A dependent
wallet acquires its required provisional key revisions under the rollback lock.
Published requirements follow the actual root or account-scoped Keychain tags,
so a copied inventory or equivalent network alias cannot erase those
requirements. Replacing a child does not commit provisional secrets absent from
the resulting wallet.

Previously unseen historical models with missing keys remain usable for a
separate account import. This mechanism does not invent missing secrets or
require every historical wallet to have a complete root inventory.

## Qualification and limits

The candidate evidence preserves failures from actual factories and actual
SelectedWalletSettings/Core Data saves. It covers intermediate writes,
write-then-error, failed saves, exact prior payloads, overlapping owners,
dependency acquisition on both sides of rollback, all seven callers after
owner release, and duplicate requests during an issued save. Public fixtures
exercise the real system Keychain domain as well as a fault-injectable store.

The final candidate record is the authority for source hashes, compiled reader,
runtime results and retained failures. A passing focused run does not replace
the required full newest-runtime suite or historical writer/current-reader
replays. Exact historical expected values are never generated by the candidate.

This is not crash-atomic or cross-process storage. A Keychain rollback failure
is surfaced to a living caller and logged otherwise; retries require retained
operation ownership. Deallocation offers best-effort cleanup, not durable
recovery from unavailable storage. An unrelated writer outside this ledger can
be protected when its bytes differ, but identical-byte external writes do not
carry transaction ownership. No physical biometric, distribution signing,
public-chain transaction or complete release-matrix acceptance is implied.
