# iOS first-owner App Attest bootstrap candidate

The native `PasskeyBackupAppAttestBootstrap` is disabled by the compiled recovery flag and has no production caller. It preserves the iOS 15 minimum and does not add an entitlement or provisioning claim. The caller must first obtain a fresh wallet-proof-bound `attestationNonce` from an authenticated owner ceremony. The adapter rejects malformed or noncanonical base64url, decodes exactly 32 bytes and passes `SHA256(decodedNonce)` as Apple's `clientDataHash`. Public synthetic Ed25519 and secp256k1 owner-authority vectors pin both resulting hashes in iOS tests. This type checks encoding; it cannot authenticate a server response on its own.

The native gateway checks `DCAppAttestService.isSupported`, calls `generateKey`, validates Apple's padded Base64 key ID as exactly 32 bytes, and calls `attestKey` with that exact hash. Its typed result contains only canonical base64url `keyId` and `attestationObject` in the server's `{kind: "app-attest", keyId, attestationObject}` shape. Native errors are sanitized, callbacks are serialized to one active ceremony, cancellation settles it once, and late callbacks cannot settle a later ceremony. Neither wallet material nor PRF output enters this adapter.

The app now writes the generated key ID and exact 32-byte nonce, ceremony ID, provisional owner subject and expiry to a new `WhenUnlockedThisDeviceOnly` Keychain item before requesting Apple attestation. It does not modify existing wallet Keychain items. Only `DCError.serverUnavailable` leaves this pending record for an explicit later attempt with the same key and `clientDataHash`; an unrelated owner or ceremony cannot take it over before expiry, and an expired challenge cannot be attested. Other native failures discard the ID. Successful attestation clears the pending item before returning a transport object. Keychain read/write/clear failures withhold the transport. This journal contains no private key or wallet secret.

The owner authority has a candidate Apple App Attest verifier; its production composition, receipt validation and real-device proof remain open. An authenticated HTTP path must still issue this exact nonce after the local wallet proof and bind the returned ceremony ID, provisional subject and expiry. The adapter validates these fields locally; it cannot establish that an HTTP response is authentic. Operator provisioning must establish the exact Team ID, bundle ID and App Attest environment. A real supported device, first-owner wallet proof, server-issued nonce, Apple attestation and end-to-end owner admission remain required. The final recovery and TestFlight gates remain blocked until provider interoperability, replacement-device recovery and independent review pass.

References: [Apple `DCAppAttestService`](https://developer.apple.com/documentation/devicecheck/dcappattestservice), [Apple `attestKey` retry guidance](https://developer.apple.com/documentation/devicecheck/dcappattestservice/attestkey%28_%3Aclientdatahash%3Acompletionhandler%3A%29), [Apple server validation](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server).

Local qualification on the exact source: an iOS 18.1 arm64 simulator passed all 14 App Attest adapter and retry tests with zero failures. The Keychain round-trip, protection-class and clear test required an ad hoc signed simulator build; the unsigned simulator correctly returned `errSecMissingEntitlement`. The earlier 32 native PRF tests and unsigned arm64 Release simulator app build passed before this change. A broader two-architecture Release simulator build compiled the app source but failed while linking its x86_64 slice on pre-existing IrohaCrypto native symbols; it is not release-artifact evidence. SwiftFormat, SwiftLint and project-file syntax checks passed. No simulator result establishes a live Apple attestation or signed in-place upgrade.
