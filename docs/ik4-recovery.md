# Retained data and emergency recovery (IK-4)

This implements the 2026-10-10 decisions addendum U0. The earlier proposal to clear the PIN after setting aside the wallet database is superseded: recovery preserves existing authentication and all keychain material.

## User paths

- Every startup failure offers retry, authenticated emergency material, previous app data, and help containing only the stable incident code. Network failures offer a fresh network store immediately for known compatibility failures, or after a second transient failure. Language failures can continue in English after a second failure, skipping only the language migration for that recovery session.
- A readable wallet store uses the import flow without setting aside any records. An unreadable user store can be set aside only after existing authentication and an explicit confirmation. Its entire SQLite family stays in `UserStoreRetained`; no keychain item or PIN is removed. An unavailable wallet list without an app PIN can reach import, retaining the emergency access entry.
- The wallet records notice, Profile > Advanced, and onboarding expose recovery access. Healthy wallet setup is independent of archive reevaluation.
- Completing onboarding/import with retained authentication verifies the existing PIN. Only a confirmed absent PIN offers new-PIN creation; an unavailable keychain cannot authorize replacing one.
- Emergency access uses the existing app PIN/biometrics. Historical installations without an app PIN must authenticate as the device owner. Enumeration and reads occur only after successful authentication. Cancellation is final for that request.
- The export inventories the literal tag conventions written by pre-multiasset and V2 releases, independently of wallet record decoding. Values are encoded as Base64 without validation, normalization, derivation, or rewriting. It excludes PINs and unrelated keychain items, and lists individual read failures without hiding other records. The warning explains that this is secret, potentially incomplete material, not a verified backup. The preview and share action are cleared when the app becomes inactive. Nothing is written to an app temporary export file.

## Retained store handling

Each startup checks archives again with current validators on disposable family copies. The Substrate check uses strict migration, without its set-aside/rebuild fallback. User archives are checked against shipped Core Data models and opened read-only on a copy; preview never performs a keychain migration. The ordinary startup migration runs after the accepted copy is restored.

Restoration is authenticated and explicitly confirmed. Validation and request persistence run on the recovery queue, with a visible busy state. The store swap is deferred to the next cold launch, before the wallet or network coordinator opens. The current live family is durably copied into a new retained archive first; the existing `CrashConsistentStoreReplacer` journal then provides rollback/reconciliation. The selected archive and previous current family remain byte-for-byte preserved. The installed copy may undergo the normal schema migration. No archive is automatically deleted, and retained roots remain included in device backup.

Contact salvage reads a bounded private copy, including its WAL, and inserts only missing addresses. The shipped contact repository uses address as its identity, so it never overwrites an existing contact with an archived contact from another chain. Every original contact remains in the archive. Recovery copy explains that applications may need reconnecting and custom nodes may need re-adding; those original records also remain available in the retained store.

## Validation

The focused suite includes all 15 historical wallet models, all 54 historical network models (including deliberately unsupported archives), preserved populated wallet identities, exact legacy/V2 key bytes, cancellation/late-authentication callbacks, foreground redaction, eight replacement interruption boundaries, off-main restore validation, contact salvage against every historical schema carrying `CDContact`, startup routing, all nine shipped locales, and scene-hosted small-screen/Dynamic Type layout.

The final source passed the full `fearlessTests` target on the dedicated iOS 27.0 simulator: **2,314 passed, 59 skipped, zero failed** (2,373 total). This includes the real Keychain tag inventory, every archive validator fixture, the existing-PIN import regression, main-thread language switching, and all recovery tests. The small-screen test scrolls to each action and verifies its window hit target; its two image attachments were inspected. The skipped cases comprise 33 pre-existing placeholders, 18 local-chain tests requiring explicit local validator URLs, four copied-device/phone-scale/historical-store fixture gates, and four legacy or environment exclusions. They do not establish release or device qualification.

The startup capture and log-filter Python suites passed 40 and 14 tests respectively. `git diff --check` passed. SwiftFormat passed for the changed recovery files; SwiftLint retains the same ten existing errors in `RootInteractor` and `RootTests` (file/function size, complexity and existing force-tries), with no newly introduced lint error. This is not a claim that whole-repository lint passes.

Evidence is under `build/reports/ik4-recovery/`: `unit-27-final-v2.log`, its result bundle and summary JSON, the inspected `ui-27-final-attachments/`, and `validated-source-files.json` containing SHA-256 identities for all 39 changed source/resource/script files. The source identities were checked again after the final run. Older-runtime validation is recorded separately below; physical-device, Release-configuration and distribution-signed upgrade gates remain open in the release checklist.

The same source also passed **165 tests, zero skips and zero failures on iOS 18.1**: `RootTests`, `StartupRecoveryPresenterTests`, `RetainedDataRestoreTests`, `MainTabBarTests` and `WalletTransactionHistoryTests`. This closes the previously pending I1 older-runtime UI gate. Both maximum-text recovery attachments were inspected on this runtime too. Evidence is `ui-18-rebuilt-v2.log`, its result bundle/summary JSON, and `ui-18-final-attachments/`.

Reproduction must build for the older destination: an iOS 27 product reused with `test-without-building` omitted `libswiftCompatibilitySpan.dylib` and could not launch on 18.1. Xcode's ordinary build for the 18.1 destination automatically added its `--back-deploy-swift-span` copy/sign step; no project/source workaround was made. The build also needs `SOURCE_PACKAGES_DIR` set to the same immutable cache passed to `-clonedSourcePackagesDirPath`, as required by the dependency-source verification phase. Both unsuccessful preparation attempts remain in the evidence directory. [Validation record](ik4-recovery-validation.json) preserves final counts, source identities, log hashes and these limitations.
